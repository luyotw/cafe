## Regression coverage

- [ ] Establish the issue-wide product baseline and current HEAD from the supplied workspace or declared repository evidence. Map the cumulative changed behavior to first-party callers and existing regression suites, including shared startup/bootstrap factories, authentication/session/logout flows, dialogs, persistence and settings consumers where affected. Use the requirements, plan and review as inputs; newly added test files and the latest correction diff are not the boundary of acceptance.
- [ ] Before execution, record a Regression Coverage table in the QA report: changed contract/shared entry, affected callers, existing test files or observable journeys, command, and outcome/evidence HEAD. Locate existing tests by the affected public behavior and call sites, even outside the changed module. Include those suites alongside new-feature tests. A changed UI interaction must be exercised through its real public sequence; do not omit old tests because their fixtures or interactions now fail. Explain exclusions with concrete dependency evidence; naming a targeted command alone is not a selection rationale.
- [ ] On correction, reconcile the previous QA coverage and every unresolved failure with the cumulative impact map. Add newly discovered callers and previously omitted tests. Reuse earlier passing evidence only when its source, test/fixture, configuration and relevant dependency boundaries still match; record that basis and HEAD explicitly. Re-run affected rows, and preserve required or blocked checks until passing evidence or an explicit requirement change closes them. A small latest diff, an unchanged test file or a previous pass is not sufficient proof for reuse.
- [ ] Run the selected existing suites and user journeys independently, retain actual completion/exit evidence, and classify each row as passed, failed, blocked, reused or pending with its owner. Keep repository-owned full-suite/CI/release gates with their existing owner; never silently filter away failures, add a new repository-wide gate, or label a targeted pass as full CI success. Route observed failures through the declared correction route; missing evidence for a QA-owned required row prevents a fully passing handoff.
