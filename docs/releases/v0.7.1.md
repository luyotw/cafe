# CAFE v0.7.1 release notes

## Release scope

CAFE v0.7.1 adds subagent-assisted planning workflows and verified native
delegation preference during kickoff. It also fixes Codex stream activity
capture, interrupted-session recovery, PR feedback curation, and kickoff runtime
alignment. It also fixes completion being blocked by additional completed
checklist records. This release integrates the completed changes from `main` and
`develop` after v0.7.0.

The `0.7.1` release number follows an explicit user request. Its scope includes
new user-visible workflow capabilities, which would ordinarily receive a minor
increment under the [versioning policy](../versioning.md).

## Subagent-assisted planning and optional QA

Two new built-in playbooks are available:

- `subagent-flow`: joint requirements and implementation planning with a native
  planning partner, followed by development with subagent reviews and PR review.
- `subagent-flow-qa`: the same path with independent acceptance QA before PR
  publication.

The `spec_plan` phase produces one combined `plan` artifact containing the
requirements specification, implementation approach, Test List, and Todo List.
The parent owns edits and decisions while the planning partner reviews the
complete draft. The existing confirmation contract governs approval of the
requirements and plan together. Assign that confirmation gate to the user in
kickoff when the user wants to approve the draft personally.

Early clarification preserves the original request and known decisions in a
provisional plan for restart-safe continuation. Draft revisions repeat the
discussion within the same phase. Development that invalidates confirmed
requirements returns to `spec_plan`; routine implementation corrections remain
in Develop. The QA variant evaluates the requirements embedded in the combined
plan, and failed acceptance returns to Develop for correction, repeated
subagent reviews, and another QA pass.

See [Built-in playbooks](../../README.md#built-in-playbooks) for selection guidance.

## Verify native delegation during kickoff

Among candidates covering the same responsibilities and QA boundaries, kickoff
prefers native-subagent workflows when the selected execution chains support the
required delegation. Every primary and configured fallback must have evidence
for the installed CLI, selected model, and effective permissions.

A planning phase requiring one partner needs one successful native launch and
parent collection. A review phase requiring two parallel reviewers needs both
launches before either finishes, both successful results, and parent collection
of both. An ordinary model probe or provider name is insufficient evidence.
The preference preserves explicit or persisted playbook choices and required
confirmation and QA boundaries. Declared `Agent` tools now map to native Gemini
and Copilot delegation tools as well.

## Stream activity and interrupted-session recovery

The Codex loopback telemetry receiver accepts batches up to eight MiB. Ordinary
native 512-record batches can exceed the previous one-MiB limit; accepting them
avoids losing live-stream observations. Diagnostics include rejected HTTP
requests and the largest request size. The activity queue remains bounded and
retains metadata without prompt text or streamed deltas.

Failed attempts can retain a verified CLI/session pair after timeout, execution
limit, or incomplete output. The phase saves the final attempt's verified pair
for an exact user-selected retry. Conflicting or invalid evidence does not
establish a resumable identity. An existing-session retry without valid identity
leaves its HumanTask pending; a legacy completed retry without the required
evidence is also rejected. Starting a fresh session remains an explicit
user-owned recovery choice.

See [Codex stream activity](../codex-stream-activity.md) for the activity and
interruption contracts.

## Feedback and checkout alignment

Completion validation checks that every required checklist gate and its
subordinate instructions remain present. Completed supplemental checks and
additive annotations can record source and Todo cross-checks without an
identical checkbox count. Required occurrences need distinct checklist items,
and every checkbox must be completed. Removing or replacing a required gate,
changing its required instructions, modifying pinned metadata, or submitting
mismatched Todo identities, fingerprints, or repository evidence still blocks
completion.

PR curation can deliver its normalized Todo List through the declared
`manual_handoff` destination when no explicit feedback route is available.
Runtime validates the receiving phase's declared input and canonical worklist,
including mixed source kinds, while retaining each runtime-assigned ID and
Source.

Standalone kickoff preparation and formatting helpers resolve the selected CAFE
checkout before importing the runtime, and their Python children inherit the
same source selection. Ordinary projects continue using their installed
runtime. An already-imported incompatible runtime is reported rather than
partially reloaded.

## Upgrade guidance

```bash
pip install --upgrade cafe-engine==0.7.1
```

Existing workflows retain their selected playbook and confirmation ownership.
Choose the new playbooks deliberately for new work and verify the required
native delegation across the selected chains. Use the deliberate helper-sync
path when updating globally installed authoring or Manager guidance.

Manager chat support and native read-only diagnostic limitations remain as
documented in the [v0.7.0 release notes](v0.7.0.md). This release adds no authority
to answer user-owned tasks or perform external mutations.

Publishing the GitHub release triggers the trusted PyPI publisher, which builds
and publishes distributions from the exact release tag.
