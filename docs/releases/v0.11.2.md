# CAFE v0.11.2 release notes

## Release scope

This patch includes develop fixes through `1136fc24`: Codex usage accounting
without exact CLI release gates, model capability cache compatibility across
CLI upgrades, and evidence requirements for feature version restrictions.

## Codex cost accounting

Request and native descendant usage no longer require `codex-cli 0.159.3`.
The CLI version remains diagnostic metadata. Compatibility is established from
recognized journal structures, exact session/thread identities, ancestry,
ownership, baselines and reconciled counters.

Per-thread usage records select only the child's exact thread ID, excluding
inherited records from other threads. Validated root observations establish
parent inclusion evidence without relying on a release string. Missing,
incompatible, overlapping or reset evidence still leaves explicit gaps and
withholds unsupported combined totals. This patch does not infer compatibility
from the absence of a version number or reprice historical costs.

## Model capability cache

Codex reasoning-effort selection can use otherwise valid `models_cache.json`
entries even when `client_version` differs from the installed CLI. The exact
model and declared supported reasoning levels must still match; missing or
unsupported capability evidence still rejects explicit effort. Existing provider
invocation controls and omitted-effort defaults remain unchanged.

## Engineering guidance

Repository guidance now requires documented, reproducible evidence for feature
gates based on provider, CLI, SDK or dependency release versions. A tested version
alone is not a supported-version allowlist. Exceptions must identify their
narrow scope, recovery path, removal condition and regression coverage.

## Upgrade and verification

Existing sessions, pending decisions, confirmed delivery contracts and stored
cost records remain readable without manual migration.

```bash
cafe update check --json
cafe update apply --token <approval-token>
```

An approved update synchronizes bundled CLI-native helpers from the installed
release. The final-commit release gate covers coverage and extended kickoff
journeys, contracts, lint, distributions, clean installation, packaged features
and workflow upgrades. These checks use controlled local evidence rather than
claiming a new live provider acceptance run. Publishing the GitHub Release
triggers trusted PyPI publication of the exact v0.11.2 tag.
