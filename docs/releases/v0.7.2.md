# CAFE v0.7.2 release notes

## Release scope

CAFE v0.7.2 fixes provider execution diagnostics, session persistence, native
Codex WebSocket activity detection, kickoff playbook recommendations, and close
checkout selection. It integrates five completed fixes from `develop` after
v0.7.1. This is a patch release with no new CLI commands or declaration formats.

## Provider diagnostics and observed sessions

Each execution attempt with a streaming output path retains its bounded stderr
snapshot in a separate private diagnostic file. Diagnostic metadata records the
file path, total and retained bytes, truncation and read status, return code,
and timeout kind. Failure records retain the diagnostic reference; retries do
not overwrite an earlier attempt's file.

Successful structured tool output no longer supplies error classification for a
nonzero provider exit. Structured provider errors and native stderr remain
error evidence; plain-output providers can still report errors on stdout.
Executor-owned idle and post-output timeouts retain their timeout classification.

Authoritative provider session identities are saved as soon as they are observed,
before the invocation finishes, including primary, same-CLI retry, and backup
attempts. Exact continuation still requires the expected session identity, and
persistence failures stop the attempt. Existing successful completion handling
for older response-only identity records is preserved. A retained session does
not establish completion or bypass the existing recovery checks.

## Codex WebSocket idle detection

The Codex activity adapter now observes native `codex.websocket.event` OTel
counters in addition to SSE and WebSocket logs. A provider can remain active
while `codex exec --json` stdout is quiet; fresh successful `response.*` counter
activity can refresh the existing idle watchdog after stdout verifies the
invocation's thread identity.

The adapter accepts new delta intervals and increasing cumulative counters;
stale or replayed exports, unchanged counters, unrelated metrics, and foreign
log sessions do not refresh the watchdog. Counter tracking remains bounded and
stores metadata rather than prompt text or deltas. Native terminal evidence is
still required for completion, and duration and output budgets remain enforced.

Invocation-only exporter settings and a copied child environment collect metrics
every second. Existing explicit telemetry destinations are protected, selected
profile configuration is respected, and `--ignore-user-config` follows the
provider's configuration behavior. The caller environment and Codex config files
are not modified.

See [Codex stream activity](../codex-stream-activity.md) for the detailed contract
and native SSE/WebSocket validation evidence.

## Kickoff recommendations and linked-worktree close

Kickoff recommendations use current confirmed scope and exclusions rather than
an earlier Manager proposal. An unconfirmed table is not a user-selected
playbook. Separate spec ownership and independent QA require concrete ownership,
acceptance, or repository-policy evidence; unresolved architecture or the number
of modules touched alone does not justify those extra boundaries.

The user's explicit native-subagent capability confirmation is accepted when it
covers the intended CLI, model, settings, and delegation requirements. A redundant
fresh native probe is not required for that setup. Every primary and fallback
must be covered, and contradictory evidence or uncovered settings still require
reassessment. Exact-model availability, authentication, and fallback smoke
checks remain required.

Closing an issue from a nested linked worktree resolves the checkout holding the
base branch from Git's worktree inventory, with the discovered project root as
fallback. It no longer walks upward looking only for a `.git` directory, which
could select the wrong checkout when the valid linked checkout has a `.git` file.

## Upgrade guidance

```bash
pip install --upgrade cafe-engine==0.7.2
```

No configuration or persisted-workflow migration is required. Existing selected
playbooks and confirmation ownership remain applicable. The diagnostic files
are per-attempt runtime outputs; workflows continue using their existing output
and recovery contracts.

See [v0.7.1 release notes](v0.7.1.md) for subagent workflow selection and the
required-checklist and Todo evidence rules retained by this release.

Publishing the GitHub release triggers the trusted PyPI publisher, which builds
and publishes distributions from the exact release tag.
