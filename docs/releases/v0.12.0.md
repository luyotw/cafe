# CAFE v0.12.0 release notes

## Release scope

This minor release includes develop through `1924df57`: shared verification
profiles (#656/#662), systematic command steps and prepared delivery (#663),
automatic receipt-based development delivery (#658), controlled same-step
correction (#664), cleanup migration (#660/#661), and startup/Codex fixes.

## Shared verification profiles

QA and CI can use the same versioned JSON manifest through project-local
`verification.profile_file` and `verification.profile` settings, or explicit
`--profile-file` and `--profile`. Profiles declare mandatory and optional suites;
`--add-suite` adds declared optional suites without narrowing mandatory coverage.

`cafe verification run --reuse-from` runs pending suites and reuses only opted-in
results whose original identity, HEAD, logs and declared file/environment/probe
context still match. Reuse-only never runs replacement suites. Fresh successful
execution and eligibility for future reuse are evaluated separately. Missing or
invalid evidence remains explicit. Existing raw-command verification remains
available when a repository has not adopted a profile.

See [Verification profiles](../verification/profiles.md) and the
[executable example](../../examples/verification_profiles/README.md).

## Command steps and automatic delivery

Playbooks can declare non-agent command execution with explicit inputs,
execution boundaries and durable results. Command execution requires the
configured sandbox to be available and does not silently fall back to an
unrestricted process. A completed matching receipt can be reused; an unknown or
failed launch cannot be blindly replayed.

New preparation requires explicit delivery choices through
`cafe prepare --set <step>.<field>=...`. Bundled development playbooks run their
delivery step automatically through the host. Action review and exact capability
approvals still precede effects. The host writes localized outcomes from actual
receipts, waits for required verification and requests existing final acceptance.
No phase agent executes the delivery skill's prose. Independent implementation
correction and review-only routes remain distinct from integration.

`cafe delivery run --issue <name> --step <delivery-step>` runs or reconciles an
already-approved bundle through the same adapters. It grants no new merge,
publication, issue or cleanup authority. Existing project catalogs retain their
declared agent delivery hooks. See [Development delivery](../development-delivery.md)
for preparation fields, receipt identity and legacy behavior.

## Controlled same-step correction

`cafe workflow-interrupt` can inspect an owned invocation or request correction
using its exact worker/workflow/step/iteration identity and concrete feedback.
Only the owned provider process is stopped; successful termination is verified
before the same-step correction handoff is published. Unknown ownership or
unverified stop refuses advancement. Recovery uses saved evidence, and resuming
the workflow remains explicit. This operation does not answer pending decisions,
reset budgets, change models, bypass review or authorize delivery.

See the workflow driver's
[supervision reference](../../src/cafe/data/skills/use-cafe-workflow/references/supervision_and_recovery.md).

## Migration: delivery before close

`cafe close` now verifies existing integration, archives the issue and cleans up
its exact branch/worktree. It does not merge. The options `--squash`, `--message`
and `-m` are removed. Complete the approved local/GitHub integration into the
configured base branch through delivery before running close. Cleanup requires
clean retained/source checkouts and exact local/remote integration evidence;
it stops on divergence or uncertain identity.

`cafe close --archive-only` retains its archival-only scope. Existing destination
checkouts remain in place. A normal source checkout selected for branch cleanup
is retained at its proven commit in detached state; an explicitly selected
managed source worktree can be removed. Historical contracts containing former
close argv remain readable with their original bytes and digests, but reading
history does not make removed options executable. Replace an obsolete plan
through the existing explicit reconfirmation route. See [Close an integrated
feature](../cli.md#close-an-integrated-feature).

New kickoff confirmations/contracts retain exact CLI/model/effort selections
without promoting selection rationale into policy. Legacy assessment inputs
remain accepted for preparation compatibility but are omitted from new contract
identity. Existing confirmed contracts are not silently rewritten.

## Startup and Codex fixes

Startup no longer treats native skill ownership metadata as an admission gate.
Legacy skill-preparation failures can recover without a prior session. Healthy
silent providers are not killed merely for lacking output, and bounded sanitized
startup diagnostics survive failures before worker runtime construction.

Codex read-only empty-scope launches contain one effective sandbox option.
Model-cache refresh timestamps and unrelated entries no longer invalidate
preflight identity; selected capability levels and actual control changes still
invalidate it. QA acceptance retains issue-wide regression coverage, and cleanup
of accepted correction branches uses the correct issue and retained receipts.

## Upgrade and verification

```bash
cafe update check --json
cafe update apply --token <approval-token>
```

An approved update synchronizes bundled CLI-native helpers from the installed
release. Review changed delivery/cleanup plans before activating them; resume
preserves existing confirmed authority. Stored sessions, pending decisions and
historical accounting retain their identities.

The final-commit gate checks coverage, extended kickoff journeys, strict contracts,
lint, distributions, clean installation, packaged profile execution/reuse and new
CLI surfaces, existing feature checks and workflow upgrades. Controlled local
evidence does not claim a new live provider acceptance run. Publishing the GitHub
Release triggers trusted PyPI publication for the exact v0.12.0 tag.
