# CAFE v0.8.0 release notes

## Release scope

CAFE v0.8.0 adds the focused bug workflow (#434), compact preparation and
streamlined development (#598), declared development delivery (#602), and an
issue-scoped rate-limit restart policy (#455).
These user-visible capabilities require a minor release under the versioning
policy. The constraints work in #493 was already released in v0.7.3.
Architecture follow-ups #532, #439 and #551 are outside this release.

## Focused bug repair

Select `bug` for a confirmed bounded defect. Diagnosis records reproduction and
failing regression evidence; repair preserves the assertion through RED/GREEN;
an independent reviewer verifies the evidence and scope. Successful review
advances to PR action review, approved delivery, and separate result acceptance.
Code corrections always return through repair and independent review. Invalid
diagnosis returns to diagnosis; three unfinished attempts require human input.

## Compact preparation and streamlined delivery

`streamlined` uses a compact confirmed contract instead of full specification
and planning. It retains cumulative file scope, provider-observed single native
review, current snapshot checkpoints and the exact approved endpoint. Changed
scope, review evidence or publication identity requires a focused handoff.
Delivery readiness alone is not evidence that a push or PR creation succeeded.

## Development action review and result acceptance

Development playbooks, including `bug`, use `delivery-review` to approve the
exact integration and selected follow-up drafts. `deliver` executes declared
host operations and presents receipts before `delivery-outcome` acceptance.
The new capabilities are `cafe.github.pr.merge`, `cafe.branch.integrate`, and
`cafe.github.issue.create`. One PR confirmation approves the displayed actions
and host capability boundaries, while separate durable records preserve each
grant. A changed manifest or action requires fresh matching approval. Legacy
proposals without displayed capability boundaries retain separate host approval.
Unknown effects are reconciled from durable attempts before any further action;
restarting a workflow does not authorize replay or broaden the selected drafts.

The `review_only` choice returns to PR review and does not complete delivery.
Result acceptance can select the exact displayed cleanup plan, archive only
while retaining the worktree and branch, or leave the environment as-is. Manager
uses the recorded choice after completion; changed receipts or cleanup plans
require fresh acceptance. Release publishing retains its existing authority
boundary. Kickoff contracts omit preference diagnostics that cannot be saved.

## Rate-limit restart policy

The default `continue_last_success` policy preserves the last successful CLI
preference and existing session continuation. Opt into `recheck_priority` for an
issue through the supported settings interface:

```bash
cafe settings update ISSUE --set 'execution.rate_limit_restart_policy="recheck_priority"'
```

After a current rate-limit interruption, the recovery HumanTask offers
`retry_configured_order`. Choosing it starts a new session with the currently
configured primary CLI/model, then uses the normal fallback order if primary is
still limited. The reset applies once to that authorized invocation. Existing
retry choices remain explicit overrides; saving a setting alone does not start
execution or answer a task. Configuration changes invalidate incompatible sticky
preferences without changing provider retry counts or delays.

The owning step's `iteration.json` records `restart_diagnostics`, including the
saved/effective policy, configured/effective CLI/model order, sticky disposition
and correlated task/result. See [settings updates](../settings-updates.md#rate-limit-restart-policy)
for preview, persistence, pending-task migration and session semantics. Approved
delivery continuations also retain settled feedback, and verified empty-feedback
handoffs resume without unnecessarily restarting PR preparation.

## Manager recovery

Eligible stopped phase agents may resume their existing session up to three
times, with 30 seconds before each retry. The original execution is not a retry.
The read-only recovery-budget helper counts existing task/results for the same
workflow, step and iteration, including user-selected recovery; new Manager
sessions and duplicate callbacks cannot renew the budget. An explicit user stop
retains the pause. Exhausted, ambiguous, cancelled, unsafe or non-resumable
executions require the existing user recovery boundary. Fresh-session selection
remains user-owned; this policy does not change lower-level transient backoff.

## Upgrade guidance

```bash
pip install --upgrade cafe-engine==0.8.0
```

Existing project playbook overrides remain authoritative. To adopt the new
flow, update the PR action-review binding, delivery declarations, hooks and
artifact inputs together; changing a skill alone cannot change the graph.
New builtin workflows need both PR action review and delivery result acceptance.
New Manager contracts use nested delivery schema version 5 with cleanup only;
Manager `deliver` commands and descriptions are no longer kickoff fields. Old
delivery preferences/templates remain inspectable diagnostics and cannot restore
execution authority. Clear obsolete preferences through the supported preference
CLI before preparing a new contract; retain existing confirmed legacy contract
bytes and exact operation bindings while finishing an old workflow.
Existing kickoff stop contracts must be reviewed against the current
`cafe playbook confirmation-gates <id>` output before continuing.

Persisted HumanTasks retain their policy snapshot and declared continuations.
An older `local-review` response must use that task's choices and original graph;
it is not approval for the new integration or issue capabilities. Keep the
original project playbook while finishing an in-flight legacy workflow, then
adopt the new builtin graph for a new issue. A saved project copy omits the
builtin-only `initial_input.legacy_presentation` flag; its workflow topology and
HumanTask continuations remain unchanged. Do not edit generated task, baton,
blackboard or delivery records to migrate authority. Existing recovery state and
legacy operation receipts remain readable through their bounded adapters.

The native skill exclusion and phase chat guidance in
[v0.7.5](v0.7.5.md#upgrade-guidance) remains applicable.

Publishing the GitHub release triggers the trusted PyPI publisher, which builds
and publishes distributions from the exact release tag.
